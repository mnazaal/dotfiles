Basic dotfiles.

* Overview

This repository root is dotfiles tree.

- shell files live at top level
- application config lives in =.config/=
- local scripts and data live in =.local/=

For zsh specifically, top-level shell files are tiny bootstraps:

- =.zshenv= sets =ZDOTDIR= to =~/.config/zsh=
- =.zshrc= and =.zprofile= forward into that directory

Repo-only files such as =README.org= and =.gitignore= are not meant to be stowed.

This setup has two profiles:

- *Laptop* = full personal workstation; assume I want everything
- *Remote server* = HPC login node or VPS over SSH; keep serious CLI/editor workflow, skip desktop and local-hardware-specific pieces

Many configs degrade gracefully when optional commands are missing, but laptop should be treated as full install.

* Deployment

Canonical deployment from repository root:

#+begin_src bash
make link
#+end_src

This runs the underlying Stow command:

#+begin_src bash
stow --target="$HOME" --no-folding .
#+end_src

Run repository checks with:

#+begin_src bash
make check
#+end_src

=make check= runs =dotfiles-doctor= and advisory shell lint/format checks when =shellcheck= and =shfmt= are installed.

The local ignore file excludes repo-only files such as =README.org= and =.gitignore=.

Do not copy only =.config/zsh=. Top-level shell bootstrap files must also be linked into =~/= so that =ZDOTDIR= and XDG variables are set before =.config/zsh/.zshrc= runs.

If SSH from Kitty prints =missing or unsuitable terminal: xterm-kitty=, the remote host lacks Kitty terminfo.

Best local-machine fix: use Kitty's SSH kitten, which copies the needed terminfo before login:

#+begin_src bash
kitty +kitten ssh host
#+end_src

Fallback for one login:

#+begin_src bash
TERM=xterm-256color ssh host
#+end_src

or add this for that host in =~/.ssh/config=:

#+begin_src sshconfig
Host host
    SetEnv TERM=xterm-256color
#+end_src

Manual fix: copy terminfo with =infocmp= and install it on the server with =tic=.

*** SSH config

The tracked =.ssh/config= carries only generic defaults: connection
multiplexing (=ControlMaster=/=ControlPath=/=ControlPersist=) and keepalives
for every host. It must not contain real hostnames, IPs, or usernames.

Real per-host entries (clusters, VPSes, git remotes) live in
=~/.ssh/config.local=, which is machine-local and never tracked. The tracked
config pulls it in with =Include ~/.ssh/config.local= at the top.

Multiplexing needs the socket directory to exist:

#+begin_src bash
mkdir -p ~/.ssh/sockets && chmod 700 ~/.ssh/sockets
#+end_src

Verify the merged result with =ssh -G <host>=.

** Kitty terminfo

If you ssh from Kitty and keep =TERM=xterm-kitty=, remote host must have =xterm-kitty= terminfo entry. Without it, colors and line editing can behave strangely.

Export terminfo entry from machine that already has Kitty installed:

#+begin_src bash
infocmp -x xterm-kitty > /tmp/xterm-kitty.terminfo
scp /tmp/xterm-kitty.terminfo user@remote:~
#+end_src

Then compile it on remote host into user-local terminfo directory:

#+begin_src bash
tic -x -o ~/.terminfo ~/xterm-kitty.terminfo
infocmp xterm-kitty >/dev/null && echo ok
#+end_src

If =tic= is unavailable or user-local terminfo is not supported, use =TERM=xterm-256color= as fallback instead.

** tmux version compatibility

Some clusters ship older tmux releases. Check installed version with:

#+begin_src bash

#+end_src

* Agent skills

This repository is the ground truth for shared agent skills. Skills that should
behave globally across machines live in:

#+begin_src text
~/dotfiles/.agents/skills/
#+end_src

GNU Stow publishes that directory into the runtime global Agent Skills path:

#+begin_src text
~/.agents/skills -> ~/dotfiles/.agents/skills
#+end_src

OpenCode and Pi discover =~/.agents/skills= directly. Claude Code reads
=~/.claude/skills=, which Stow also populates from the same store via the tracked
=.claude/skills -> ../.agents/skills= symlink (unfolded into per-file links). So
one tracked skill store is shared by all three agents.

Install new skills from the dotfiles root with a project install, not a global
install:

#+begin_src bash
cd ~/dotfiles
bunx skills add <repo> -a universal --skill <name> --copy
#+end_src

To install every skill from a source repository into only =.agents/skills/=,
use =--skill '*'= with the universal agent target:

#+begin_src bash
cd ~/dotfiles
OPENCODE=0 bunx skills add <repo> -a universal --skill '*' --copy -y
#+end_src

Do not use =--all= for this workflow. In the =skills= CLI, =--all= means
"install all source skills into all detected agents", so it may create extra
agent-specific project directories such as =.kiro/skills=, =.pi/skills=, or
=.pochi/skills= (and would try to turn the tracked =.claude/skills= symlink into
a real directory). If that happens by accident, remove the unwanted generated
directories and keep only =.agents/skills/<name>/= (plus the intentional
=.claude/skills= symlink).

For =andrehuang/researcher-pack=, install only its skills into the shared
universal skill store with:

#+begin_src bash
cd ~/dotfiles
OPENCODE=0 bunx skills add andrehuang/researcher-pack \
  -a universal \
  --skill lit-search \
  --skill paper-read \
  --skill research-companion \
  --skill research-session \
  --skill weekly-review \
  --skill orchestrate \
  --copy \
  -y
#+end_src

Equivalent shorter form:

#+begin_src bash
cd ~/dotfiles
OPENCODE=0 bunx skills add andrehuang/researcher-pack -a universal --skill '*' --copy -y
#+end_src

The =OPENCODE=0= prefix is only for running the installer from inside an
OpenCode session. It prevents the local OpenCode git reference hook from
blocking temporary clones used by the skills CLI.

Notes:

- Do not use =-g= / =--global= for this workflow; it writes outside the repo.
- Use =bunx skills= rather than =npx skills= to match this repository's Bun-based tooling.
- Use =-a universal= so the project target is =.agents/skills/=.
- Use =--skill '*'= for "all skills from this repo"; do not use =--all= unless
  you intentionally want every detected agent target populated.
- Use =--copy= because Stow already handles symlinking into =~/=.
- Commit =.agents/skills/<name>/SKILL.md= like any other dotfile.
- Keep =skills-lock.json= if the CLI writes it; it records source repository,
  skill path, and content hash for installed skills.
- After adding or moving skills, publish with:

#+begin_src bash
stow --target="$HOME" --no-folding .
#+end_src

If =~/.agents/skills= already exists as a real directory, move its contents into
=~/dotfiles/.agents/skills= before stowing to avoid conflicts.

** Removing or updating skills

Update tracked skills to their upstream latest (driven by =skills-lock.json=):

#+begin_src bash
cd ~/dotfiles
bunx skills update              # all tracked skills, or: bunx skills update <name> ...
#+end_src

Removal is manual. Because skills are installed with =--copy= (Stow owns the
symlinking), =bunx skills remove= does NOT delete the copied files — it only
touches agent registrations and reports success while leaving the universal
store intact. To actually drop a skill from the shared store:

#+begin_src bash
cd ~/dotfiles
rm -r .agents/skills/<name>                                # source of truth
rm -r ~/.agents/skills/<name> ~/.claude/skills/<name>      # deployed copies
#+end_src

Then delete the skill's entry from =skills-lock.json= (keep the JSON valid) and
commit both changes. Re-running =make link= will not prune orphaned links on its
own; remove the deployed copies as above, or restow with
=stow -R --target="$HOME" --no-folding .=.

** Pi subagents for Researcher Pack agents

Researcher Pack also ships agent prompt files such as =brainstormer=,
=idea-critic=, and =research-strategist=. Use those as Pi custom subagents, not
as skills.

Pi user-agent source of truth in this repo should be:

#+begin_src text
~/dotfiles/.config/pi/agent/agents/*.md
#+end_src

After stowing, Pi sees them at:

#+begin_src text
~/.config/pi/agent/agents/*.md
#+end_src

Convert frontmatter to Pi's =pi-subagents= schema. Keep =name= and
=description=, keep the prompt body, and drop Claude/OpenCode-only fields such
as =mode: subagent=, =permission=, =temperature=, and =allowed-tools=.

Example Pi subagent frontmatter:

#+begin_src yaml
---
name: idea-critic
description: Stress-tests research ideas for novelty, impact, timing, feasibility, competition, nugget, and narrative
systemPromptMode: replace
inheritProjectContext: true
inheritSkills: true
thinking: high
tools: read
skills: lit-search
---
#+end_src

Use =.pi/agent/agents= for Pi agents rather than =.agents/=. Pi has legacy
project discovery for =.agents/**/*.md=, and using that path risks treating
=.agents/skills/*/SKILL.md= as agents.
