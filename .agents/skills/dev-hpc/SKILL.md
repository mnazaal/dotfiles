# Skill: Dev HPC

## Purpose

Get a project's experiments onto a SLURM cluster and results back, reproducibly, driven from a laptop.

## Never run heavy compute on a login node

- Any multi-minute CPU/GPU job — test suite, executing docs/notebook build, training, data prep, large enumeration — runs on a *compute node* via `sbatch`/`srun`, never bare on the login node. This binds the commands you **hand the user** too: give the `sbatch scripts/*_slurm.sh` or `srun --pty …` form, not a raw `pytest`/`make`/`python heavy.py` — suggesting a bare heavy command for a cluster is the same violation as running it yourself. Login nodes are shared; admins kill heavy jobs there and may suspend the account.
- Prefer a hard guard on the heavy path so the mistake can't recur: refuse when there's no allocation (`$SLURM_JOB_ID`/`$PBS_JOBID` unset) AND the hostname matches `*login*`, with an explicit override env for edge hosts. Point the repo's docs/scripts at the batch wrapper, not the raw command.

## Code + Env Sync

- Sync code to the cluster over git (push to a remote/bare repo the cluster pulls). rsync is for *results only*, one-way.
- Pin cross-machine deps as git deps at an explicit commit (`tool.uv.sources.<pkg> = { git = "ssh://git@github.com/owner/repo.git", rev = "<sha>" }`), never an editable local path — a path dep can't resolve identically on the cluster. Use the `ssh://git@host/owner/repo.git` scheme; uv rejects the `git@host:owner/repo` shorthand ("relative URL without a base").
- `.venv` is per-machine: `uv sync` on the cluster, never rsync it. Cluster-only extras (GPU wheels) install there.
- Install on the cluster with `uv sync --frozen --extra <X>` (or `--locked`), not a bare `uv sync`: `--frozen` uses the committed lockfile verbatim instead of re-resolving. A bare `uv sync` against a stale/differently-resolved lock rewrites `uv.lock` on the cluster — diverging from the laptop, and (with a git-reset sync tool that refuses a dirty tree) blocking the next code sync until you `git checkout uv.lock`.
- Extras installed via `uv sync --extra X` stick in `.venv`, but a later bare `uv run ...` (without repeating `--extra X`) auto-resyncs the env to the base dependency set first, silently pruning the extra back out. Either pass `--extra` on every `uv run`, or activate the venv and call `python` directly — that skips the resync.

## GPU Wheels

- Pick the CUDA extra by the node's *driver* version, not any installed toolkit: jax `cuda12` needs driver >=525, `cuda13` needs >=580 — verify current thresholds at docs.jax.dev, don't trust memory.
- Driver version isn't the whole story — CUDA major versions also drop support for older GPU *architectures* independent of the driver floor, e.g. cuda13 requires SM>=7.5 and silently excludes Volta/V100 (SM 7.0) even on a driver that clears 580. Check `nvidia-smi --query-gpu=compute_cap` against the target release's minimum SM, not just its driver requirement, especially when the partition spans multiple GPU generations.
- The login node has no GPU; `nvidia-smi` only works inside a job: `srun --gres=gpu:1 --time=00:05:00 --pty nvidia-smi --query-gpu=name,compute_cap,driver_version --format=csv`.
- Keep the GPU extra optional so the laptop stays CPU-only.

## Submission (hydra + submitit)

- **Every SLURM task must clear the admin minimum wall-time — treat ≥2 min as the floor unless the site policy says otherwise. Jobs that finish in seconds violate cluster etiquette and can get the account flagged/suspended** (same class of admin-enforced floor as the login-node rule). The trap is a `--multirun` that fans a sweep into cells each doing trivial work — load-model-then-one-inference, a handful of pairs, tiny-N generation. Fix by BATCHING short units into one task: loop the sweep points *inside* the task callable (one job processes many datasets/models/seeds), or coarsen granularity, until each cell clears the floor. Estimate per-cell wall-time from a known rate BEFORE launching and merge any sub-floor cell; model *loading* time does not reliably cover it (a 3B load + one prompt can still finish in seconds). Binds handed commands too — fanning into seconds-long cells is the same violation whether you or the user runs it.
- **Launch through the hydra-zen entry point — never a hand-written `sbatch` or bash launcher:** `python -m <pkg>.run experiment=<name> <overrides> hydra/launcher=<cluster> --multirun`. The launcher config *is* the sbatch — submitit emits the `#SBATCH` for you; a `scripts/*.sh` that writes `#SBATCH`, calls `sbatch`, or wraps a standalone `scripts/` script is the anti-pattern. If the task callable lives in `scripts/`, promote it into the package first (see the reachability bullet below: submitit unpickles it on the worker). The only sanctioned launch `.sh` is a thin `reproduce_main.sh` that itself calls that same `python -m … run`. An interactive `srun --pty` *loop over a standalone script* is this same anti-pattern in disguise: `srun --pty` is for a single interactive command or a hardware check, NOT for running a sweep as a shell `for`-loop — a multi-cell sweep, **including open-weights-model (LLM) answer/probe generation**, goes through submitit like any other experiment (which also lets you batch cells to clear the wall-time floor above).
- Launch via `hydra-submitit-launcher`; each cluster/partition is a launcher config (partition/gres/mem/timeout) registered as hydra-zen code — a `SlurmQueueConf` in the config store, not YAML, to keep config IDE-navigable (`dev-ml-infra`). Guard the plugin import: `from hydra_plugins.hydra_submitit_launcher.config import SlurmQueueConf` fails at module load without the launcher installed, so wrap it `try/except ImportError` and register the launcher only when present — the config layer and local `--multirun` then load plugin-free; only `hydra/launcher=<name>` needs the extra.
- Before fanning out a comparison sweep, settle its design via `research-run`'s Before Launching checks — seeds sized from pilot variance, arms paired on seed, a regime where the axis still moves the metric, and the comparison of interest named. Cluster time is the expensive way to discover a design was underpowered, and no re-analysis recovers it.
- `--multirun` is REQUIRED for the launcher to engage — even for a single job. Without it Hydra runs in-process locally.
- submitit shells out to `sbatch` itself, so submission runs *from* the cluster; it can't launch from the laptop.
- Pin each run's output dir under the rsync'd results dir, keyed on a known config name — `${hydra.job.name}` resolves to hydra-zen's wrapper module, not your script.
- A `--multirun` sweep names each cell's output subdir by `${hydra.job.num}` (0,1,2,…), NOT by its sweep parameters — so re-running only the missing or failed cells restarts numbering at 0 and OVERWRITES the earlier cells instead of filling the gaps. Re-run the subset into a SEPARATE tag (`<tag>_fill`) and have the read-out merge across tags by semantic key (the sweep params: seed, arm, …), so a cell is identified by what it *is*, not its job index. Never re-run a partial sweep into the original tag.
- Any code the task function references must be reachable from the installed package, not a sibling script — `from other_script import fn` between two `experiments/*.py` files works locally (the script's own dir lands on `sys.path`) but submitit's remote worker unpickles the job in a different process/cwd, so it can't find `other_script` and dies with `ModuleNotFoundError`. Move shared logic into the package proper.
- The local driver process blocks the shell until the submitted job(s) finish (it polls submitit for results) — for interactive convenience it may run under tmux/nohup/backgrounding rather than tying up the terminal. When the driver result is verification evidence, do not `disown` and lose the exit status: capture stdout/stderr, retain the PID, and record its exit status, or use scheduler status (`sacct`) as the explicit evidence source. Once it's printed the submitted job ID(s), Ctrl-C only kills the local polling loop, not the Slurm job — submission already reached the scheduler.
- **Submitted ≠ running — verify before recording a launch as in-progress.** The driver/launcher returning (or a wrapper's `launched (pid …)` line) means submission reached the scheduler, NOT that the job cleared config composition. A job that dies in seconds *before* the task body — a bad override, a failed config composition — leaves an early non-zero `.exit`/`_result.pkl` and zero output, indistinguishable from "still starting" if you only see that the launcher returned. Before trusting a launch — especially before writing "running" into a `session-handoff` — confirm `squeue`/`sacct` shows `RUNNING`/`COMPLETING` (not `FAILED`/absent) AND the first expected output artifact exists.
- **A hydra task exception exits ZERO — the logs and `sacct` both report success.** Once composition succeeds, hydra catches the task callable's exception into `JobReturn`, so the submitit worker returns normally: the `.out` ends "Job completed successfully", and `sacct` shows `COMPLETED`. The truth lives only in `.submitit/<jobid>/<jobid>_0_result.pkl`, which unpickles to `("success", JobReturn(..., status=JobStatus.FAILED, _return_value=<the exception>))` — note the outer `"success"` is the *submitit* status and lies about the task. Read `JobReturn.status` AND confirm the expected artifacts exist on the *consumer's* path before reporting any outcome; a task-body failure is exactly the class that `sacct` cannot see. Cheap corroborating tells: implausibly short `Elapsed` for the work claimed, and a params/metrics file holding only the fields written before the task body ran. An in-task "loud failure beats a silent no-op" artifact check cannot help here — it sits *after* the raising call.
- That driver process also imports the task function's full module (jax included) on the *login node* before submitting, even for a GPU-launcher override — expect a harmless CUDA-init warning there (no GPU on the login node). Don't force `JAX_PLATFORMS=cpu` to silence it on a GPU job: `sbatch` inherits the submitting shell's environment by default, so that would also force the actual compute-node job onto CPU.
- A precision/config flag set by a *runtime call* in your entry module (`jax.config.update("jax_enable_x64", True)`) can silently revert on the compute node: submitit's worker unpickles the job callable and may not re-run the entry module's top-level code (cloudpickle can serialize the callable by value), so the flag is never applied and the job runs float32 — invisible unless you assert dtype. Set it as an env var in the launcher `setup` (`setup: ["export JAX_ENABLE_X64=1"]`) so JAX reads it at import, independent of how the callable was serialized.
- **Never hand over a launch whose code path nothing has executed.** A cluster-only path — GPU `device_map`/dtype, a new extra, a larger model, anything the laptop cannot import — is invisible to the local test suite, so "tests pass" and "the config exposes the flag" are not evidence it *runs*. Before handing it over, resolve the path's new imports against the declared extra (`device_map=` pulls `accelerate`, which a CPU/float32 path never needed) or execute the smallest variant that touches the same line. If it stays unexercised, say so in the handover, so the first run is understood as the test rather than the result.
- A `--multirun` sweep fans each cell out as an independent Slurm array task, so don't serialize a separate timing/pre-flight phase to "size" it. If per-cell cost is uncertain, over-provision `timeout_min`/`mem_gb` modestly and read the real `Elapsed`/`MaxRSS` from the sweep's own `sacct`; reserve a 1-cell pre-flight for catching a *systematic* crash cheaply, not for sizing. A prior run of the same config is the strongest feasibility evidence -- trust it over a fresh timing cell.

## Recurring batch jobs (a gate, not a sweep)

- The hand-written `#SBATCH` script that Submission calls an anti-pattern is SANCTIONED for a recurring *single* job — a test-suite gate, a docs build. Those are one job with a fixed config, not a parameter sweep; submitit buys nothing and costs a launcher config. That rule is about experiments; read it that way rather than concluding this skill does not apply to the gate script in front of you.
- **A node-speed probe reports THROUGHPUT over the whole allocation, so it scales with the cores requested. Divide it by cores before comparing two runs whose allocation differed.** Used raw it manufactures both speedups and regressions: it will call a node "1.8x faster" that is identical per core and merely has more cores, and then make a lane look far off a "packing bound" computed from the same bad ratio. Corroborate any conclusion drawn from a ratio by measuring the mechanism directly — a test blamed on thread starvation that runs at ~100% CPU was never thread-starved.
- **A cluster checkout is mutable shared state, and a running job reads it throughout.** Any handover step that changes it — `pull`, `checkout`, `merge` — carries the precondition *"only after the running job reports"*. Without it the job's own HEAD-moved guard voids a run that was minutes from finishing, and that guard can only detect the race, never prevent it.

## Results

- Pull one-way, cluster→laptop, `rsync -avz` (never push back) — safe to run mid-job.
- Gitignore generated output — `results/`, the single generated-output root, which holds hydra's `outputs/` and `multirun/` (`dev-ml-infra` owns the layout): synced, not versioned.
- Result dirs accumulate from failed/OOM-killed/timed-out jobs too. Filter what you pull by `sacct -j <job_id> --allocations` keyed off each run's `.submitit/<job_id>/`, rather than a hand-rolled success marker. Only within `sacct`'s retention window (~30 days typically). `sacct` is authoritative for what the *scheduler* did — non-zero exits, OOM kills, timeouts — but NOT for whether the task body succeeded: a caught task exception exits 0 and reports `COMPLETED` (see Submission). Pair it with `JobReturn.status` and artifact presence.

## Sandbox Handoff

- Operations needing SSH to a remote — writes (push/clone of a private repo, `uv sync` resolving a git dep, first host-key accept) AND read-only status/pulls (`ssh <host> squeue`/`sacct`, `rsync` of results) — fail in a sandboxed agent session. Hand the exact command to the user (`!` prefix) **in the chat message itself — recording it in a PLAN/doc section is necessary but not sufficient, and a pointer to that section is not a substitute**; don't retry it yourself.
