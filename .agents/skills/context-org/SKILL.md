# Skill: Context Org

## Rules

- Follow host/global storage policy. If unclear, ask where to write.
- Preserve provenance: source path/URL, date, summary, tags, related links, next action.
- Never write into personal note stores unless policy or user explicitly allows it.
- Prefer Org headings/properties/tags for Org artifacts.

## Store Layout

`~/org` is `org-directory`. **Agents are read-only across all of it** — propose
edits in chat as applyable snippets; the user applies them in Emacs.

- `~/org/agenda/` — the task and calendar layer.
  - `inbox.org` — capture target for `org-capture` "t".
  - `inbox-recurring.org` — recurring items; every entry carries a `SCHEDULED`.
  - `primary-gcal.org`, `aalto-outlook.org` — GENERATED by
    `.local/scripts/cal-sync-cron` from ICS feeds and overwritten on each run.
    Read them for what is scheduled; never treat them as editable.
  - `data/projects.org` — listed in `org-agenda-files` but may not exist.
- `~/org/roam/` — org-roam knowledge base, ~885 notes. Read a specific note when
  the user names one; never scan or index the tree wholesale.
- `~/org/agents/` — agent-generated wiki output.

The agenda is a DATE view: an item carrying neither `SCHEDULED` nor `DEADLINE`
never appears in it. That is this store's dominant failure mode — captured
items with no date become invisible and rot, while everything dated stays live.
So when surfacing tasks, read `inbox.org` and `backlog.org` directly; the
agenda does not cover them.

## Workflow

1. Identify target store and permissions.
2. Normalize content with provenance.
3. Choose heading/file shape that matches existing notes.
4. Write only requested/allowed artifacts.
5. Report path and next action.
